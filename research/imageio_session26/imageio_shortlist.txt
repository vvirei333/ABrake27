### #1 — GPSCopy (ImageIO, EXIF/TIFF GPS IFD parser) — CONFIRMED real bug, silently patched

  Guard check (GLM criterion: does it validate INPUT, i.e. file-derived offset/length?): YES.
  checkCapacity/checkInitializedLength both compute `(this->base + this->{capacity,initLength})
  - ptr` and throw `OutOfBounds` (new C++ exception class, real vtable/typeinfo present) if the
  result is negative OR smaller than the requested read size. This is a textbook bounds-check
  guarding a buffer-relative pointer against both the full allocated capacity AND the actually
  populated ("initialized") length — two separate checks, which rules out this being just a
  cosmetic assert (GLM anti-pattern "nil-guard after isKindOfClass" does not apply here; this is
  numeric range validation on parser-controlled offsets, not a type check).

  Downstream isomorphism (GLM criterion: is everything after the guard byte-identical?): YES, in
  the strongest form available for this case — the raw read primitive itself
  (`read32`/`read32Unchecked`) is **byte-for-byte identical** between builds (confirmed instruction
  by instruction), and the caller `adjustIFDOffsets(IFDData*, int, int)` is the same call in both
  builds' `processData()`. What changed is purely the NUMBER of guard calls wrapped around the
  existing read sites: **stable's `processData()` calls the raw `read32()` 3 times with ZERO
  bounds-check calls anywhere in the function body** (only other call is the one
  `adjustIFDOffsets`); **beta's `processData()` has the exact same overall shape but with 42 calls
  to `checkCapacity`/`checkInitializedLength`/`pointerToOffset`/`read32Unchecked` combined**,
  i.e. a bounds check inserted before essentially every pointer dereference in the IFD-walking
  loop. This is the GLM pattern applied at *every read site in a loop* rather than once at a
  function head, because that's the actual shape of the bug surface (a multi-field IFD struct
  walk, not a single-entry-point function).

  One-shot test (GLM criterion): stable, given a GPS IFD with an offset/count field that points
  past the actual buffer, returns whatever `read32` happens to read from out-of-bounds memory
  (classic OOB read — garbage GPS data, best case; a crash or info leak, worse case, depending on
  what's mapped past the buffer). Beta, given the same input, throws `OutOfBounds` and aborts the
  copy — valid input produces identical output in both builds; malformed input now fails cleanly
  instead of reading OOB. Matches GLM's "validation always gives less" rule exactly.

  Assessed severity: **out-of-bounds READ, confirmed by evidence; OOB WRITE not ruled out** — the
  class is named `GPSCopy` (implies writing GPS data into a *new* output file/buffer via
  `writeOutputFile`), and `pointerToOffset`/`checkCapacity` operate on what reads like a single
  shared buffer struct (base+capacity+initLength fields at the same offsets used by both the
  read-side checks), so the same offset-translation logic plausibly also gates write-side access
  into that buffer — not traced in this session (would require disassembling
  `readInputFile`/`writeOutputFile` and whatever drives the write path). Triggerable via: an EXIF
  GPS IFD in a JPEG/TIFF/HEIC file processed through whatever OS-level flow invokes
  `GPSCopy::copyFileWithGPSInformation()` (not identified in this session — likely Photos.app
  metadata-copy/location-redaction path, i.e. "Remove Location" or similar; not confirmed).

  Artifacts: `/tmp/imageio_out/GPSCopy_beta_*.asm` (5 new methods), `GPSCopy_stable_read32.asm`,
  `GPSCopy_{stable,beta}_processData.asm` (265 vs 486 lines).

### #2 — DDS/ASTC "image dimensions overflow" guard — lead only, not traced to completion

  New explicit overflow-check error string exists in beta, plus a new `CreateReader_DDS_ASTC()`
  factory and `DDSDXGIFormatIsASTC()` helper. Did **not** find the actual guard instruction or its
  containing function this session — `CreateReader_DDS_ASTC()` itself (46 lines, disassembled) is
  just a constructor/factory and does not reference the overflow string; the real check is in
  some other (larger, not-yet-identified) decode function. Flagged for follow-up, not confirmed.

### #3 — rlebuf allocation size format widening (%d -> %llu) — lead only, not traced to completion

  Error-message format specifier for an RLE-decompression buffer allocation changed from `%d`
  (32-bit) to `%llu` (64-bit unsigned) between builds — strong circumstantial signature of an
  integer-overflow-class fix in a size computation (narrow accumulator silently wrapping/
  truncating on large dimensions, undersized allocation, subsequent OOB write during RLE
  decompression). Did **not** locate the containing function this session (no xref-to-string-
  address search available in the `ipsw` CLI surface used; would need a full in-cache xref pass
  or a brute-force scan of candidate RLE-related functions). Flagged for follow-up, not confirmed.
